Replicate This v2.0 — Design Specification
Date: 2026-04-17 Organization: FORRT / Replication Journal Federation Status: Approval Needed for Implementation


________________


1. Overview
Replicate This is a community-driven, public registry for nominating published research papers that merit independent verification through replication or reproduction. v2.0 transitions from a static registry to an interactive platform where researchers can nominate studies, claim replication intent, form collaborative working groups, and signal community priority through voting.


The platform is designed around two core constraints that shape every decision:


* Zero-PII compliance with German Datenschutz (GDPR) — no names, emails, or identifying data are persisted to the database
* Zero infrastructure cost at rest — serverless architecture on Vercel with Supabase, near-$0 to host

3. Visual Design
Direction: Clean & Accessible


Light backgrounds, neutral whites[c], green accent (#059669), sans-serif typeface. Designed for a broad academic audience — approachable and readable, not sterile. Reference aesthetic: Wikipedia meets Linear.


Status badges use semantic colour: green for approved, amber for in_progress (displayed publicly as "Claimed / In Progress"),[d] grey for pending (admin-only view).


________________


4. Architecture Approach
Hybrid: BaaS-first for public surfaces, Server Actions for private/complex logic.


* The public registry (nominations list, voting, DOI lookup) uses Supabase RLS for data access — simple, fast, low overhead
* The collaboration hub[e] (private working groups, live chat, claim handshake) is fully gated by server-side membership checks in Next.js — RLS acts as a second enforcement layer, not the primary gate
* This keeps simple features simple and gives explicit control where permissions are complex

FROM votes

6. Authentication & Privacy
Providers
Google, GitHub, ORCID (via OIDC using genericOAuth plugin). ORCID's sub claim is the 16-digit iD — already a pseudonymous academic identifier by design.
Zero-PII Hook
export const auth = betterAuth({


  databaseHooks: {


    user: {


      create: {


        before: async (user) => {


          const hashedId = sha256(user.id + process.env.UID_PEPPER);


          const dummyEmail =


            sha256(user.email + process.env.EMAIL_PEPPER) +


            "@privacy.forrt.org";


          return {


            data: {


              ...user,


              id: hashedId,


              name: "Anonymous Researcher",


              email: dummyEmail, // Satisfies unique constraint; real email never stored


              image: null,


            },


          };


        },


      },


    },


  },


  advanced: {


    cookiePrefix: "__Host-better-auth",


    useSecureCookies: true,


  },


});


Account linking: The deterministic sha256(rawEmail + EMAIL_PEPPER) dummy email is stable across providers that share the same underlying email address — account linking works without storing the real email.
Session & Deletion
* Sessions: httpOnly, sameSite: lax, secure, server-only (__Host- prefix)
* Delete account: purges the users row; cascades to all activity via ON DELETE CASCADE; nominations.nominator_uid set to NULL (public scientific records are retained)
GDPR Notes
* UIDs are pseudonymised, not anonymised. Treated as personal data internally.
* Privacy policy must state: emails are processed transiently for notification purposes and never persisted to disk.
* Right to erasure: single-click delete, instant effect.

7. Nomination & Moderation Pipeline
Submission Flow
1. Logged-in user submits form: DOI, discipline, justification
2. Server Action normalises DOI (toLowerCase().trim())
3. Checks nominations for existing non-rejected entry with same DOI — returns "This study has already been nominated" with a link if found
4. Calls Crossref API with AbortController (5-second timeout) and a User-Agent: mailto:admin@forrt.org header to join the Crossref Polite Pool (faster, less rate-limited) — on timeout, returns friendly error; nomination is not written[l]
5. On success: writes nominations row with status: pending, caches Crossref metadata into metadata JSONB
6. Creates in_app_notifications for all maintainer role users
Moderation Dashboard (/admin)
* Protected route — middleware checks maintainer role; notFound() if not
* Supabase Realtime subscription on nominations filtered to status: pending — live badge on new arrivals
* Pending tab: paginated list showing cached title, discipline, justification, researcher token (user_uid.slice(0,6)), submission date
* Approve: status → approved, logged to moderation_logs
* Reject: requires reason field; status → rejected, reason delivered to nominator via in_app_notification (type: nomination_rejected), logged
* Archived tab: shows rejected nominations; Undo action resets to pending, logs reversal
Status Flow
pending → approved → in_progress


    ↓


 rejected  (admin override, any time before in_progress)


Admins can manually override status at any point before in_progress.

8. Community Voting
* Gated[m][n]: user must be logged in and account must be older than 24 hours (created_at < NOW() - INTERVAL '24 hours')
* Server Action toggle: no vote → insert; same vote → delete (un-vote); opposite vote → update
* UNIQUE(nomination_id, user_uid) enforced at DB level
* Score computed from nomination_vote_totals view — never cached on the nomination row
* Registry default sort: score DESC, secondary last_activity_at DESC; additional sort by created_at via query param
* Frontend: optimistic UI via useOptimistic — immediate increment/highlight, server rollback on failure
* ORCID vote weighting: future feature, implementable as a view-level change only — no schema migration required


________________


9. Collaboration & Working Groups
Claim[o] Submission
* "Claim this study" button visible on all approved and in_progress nominations (groups stay open)
* Claimant writes a pitch message (expertise, lab readiness, timeline)
* Server Action inserts claims row with status: pending
* in_app_notifications sent to nominator ("New claim on your nomination") and claimant (confirmation)
Nominator Vetting
* Nominator's dashboard lists all pending claims with researcher token and pitch message
* Clicking the token triggers a Server Action that fetches the claimant's public ORCID biography or GitHub profile on-the-fly and renders it in a modal — no profile data written to DB
Handshake
* Accept: DB transaction fires accept_claim_transaction trigger — creates working group, adds members, sets nomination in_progress; claimant notified
* Decline: claims.status → rejected; nominator may add a note; claimant notified
* Multiple claims can be pending simultaneously; accepting one does not auto-reject others
Collaboration Hub (/hub/[group_id])
Access gated by server-side membership check in layout.tsx — returns notFound() for non-members. RLS on hub_messages enforces membership as a second layer.


Three panels:


1. Info — member tokens, nomination metadata, shared external links (hub_links). Any member can add a link with a label.
2. Message board — threaded posts (hub_posts) with parent_id for replies. Async, not real-time. For longer updates and decisions.
3. Live chat — hub_messages via Supabase Realtime, subscribed only after server confirms membership. Persisted for continuity; ephemeral in feel.
Ghost Nominator Recovery[p]
If the original nominator becomes unresponsive, an Admin can use "Promote to Nominator" on any active replicator in the group — updates working_group_members.role, logs action to moderation_logs with required reason.

10. Inquiry System
Third parties (logged-in, non-group-members) can send an inquiry from any nomination's public page.


Flow:


1. Server Action writes to inquiries with delivery_status: pending
2. Creates in_app_notifications for all working group members
3. Fetches recipient emails transiently: queries Better Auth's accounts table for the recipient's stored OAuth access token; if the token is expired, uses the stored refresh token (offline_access scope requested at OAuth handshake) to obtain a fresh one before calling the provider's userinfo endpoint in-memory
4. Sends via Postmark (EU data region); logs Postmark's response status to inquiries.delivery_status
5. Email addresses discarded immediately — never written to disk


Note: Email delivery is best-effort. ORCID accounts may have private-by-default emails, and token refresh can fail if the user has revoked access. The in_app_notification is the primary delivery method; the Postmark email is a bonus layer.


________________


11. Public Registry
* Lists all nominations with status in (approved, in_progress)
* Each card: cached title, authors, journal, year (from metadata), vote score, status badge, discipline tag. The in_progress status renders as "Claimed / In Progress" on the public badge to preserve the v1 vocabulary users expect
* Filterable by discipline, status
* Sorted by score DESC / last_activity_at DESC by default
* Claim button visible on all non-pending entries
